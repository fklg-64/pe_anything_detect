# 処理時間の内訳と高速化

OpenVINO 版（FP32・`ov_num_thread: 4`）の処理時間。2026-10-24 に、**NumPy の BLAS のスレッド数を 1 に制限**（`core/openvino/runtime_utils.py`）し、精緻化の NumPy 段を**外接矩形の中だけで処理**（`core/common/mask_utils.py`）した。最終マップは変わらない（17 枚で画素差 0、ランダム 600 ケースで旧実装と一致）。

## 結論

| | 変更前 | BLAS 1 スレッド | + NumPy 段の外接矩形処理 + 隙間埋め（現在） |
|---|---|---|---|
| **合計（中央値）** | **251.7ms** | **180.4ms**（−71.3） | **176.7ms**（−3.7。NumPy 段の外接矩形処理の −4〜5ms と、隙間埋めの +1ms 程度を含む） |

- 主因は、**伝播（`use_edgetam_clustering`）が持ち込んだ 1024×256 の行列積が、BLAS の 20 スレッドを起こし、OpenVINO の推論とコアを取り合っていた**こと。EdgeTAM エンコーダー・デコード・NumPy 段が、遅くなっていた。
- 以前の AND 版（206ms）には大きな行列積が無く、この競合は起きていなかった。伝播に置き換えた直後の測定値（約 240〜260ms）は、この競合の分だけ遅かった。
- スレッド数（`ov_num_thread`）は増やさない方針で、4 のまま。
- 測定のたびに PC の状態で全体が動く（PE が 77〜88ms）。同じ測定を 3 回行った結果は、変更前 262.7 / 265.8 / 251.7ms、BLAS 1 184.0 / 182.2 / 180.4ms、現在 181.7 / 184.0 / 176.7ms（それぞれ別の測定回。この表は最後の測定）。
- 本体の測定ツール（`exp_timing.py`、develop.py のサンプル 17 枚 + 合成 24 枚、隙間埋めの前）でも、**252.0ms → 179.4ms**（実画像 264.0 → 179.4、合成 245.1 → 179.9）。

## 1. 内訳（中央値、ms）

実画像 17 枚（develop.py のサンプル）+ 合成 12 枚、5 周、別プロセスで 2 回ずつ交互に測った平均（`tools/experiments/crack_fix/bench_modes.py`。再現手順は §6）。1 回ごとの合計は 変更前 247.9 / 255.4、BLAS 1 180.6 / 180.1、現在 178.1 / 175.2。

| 段 | 変更前 | BLAS 1 | + NumPy 段の外接矩形処理 + 隙間埋め（現在） |
|---|---|---|---|
| 画像前処理 | 3.7 | 2.6 | 2.6 |
| EdgeTAM エンコーダー | **55.5** | **32.3** | 32.0 |
| PE（画像特徴） | 82.3 | 83.1 | 82.7 |
| 粗い前景（KMeans・クラスタ代表・伝播） | **19.1** | **14.8** | 14.7 |
| 精緻化 合計 | **74.0** | **43.7** | **42.9** |
| └ EdgeTAM デコード（約 4 回） | **47.2** | **25.4** | 25.4 |
| └ NumPy / OpenCV の後処理（隙間埋めを含む） | **30.5** | **21.3** | **18.4** |
| **合計** | **251.7** | **180.4** | **176.7** |

## 2. BLAS で速くなった処理

| 処理 | 変更前 → BLAS 1 | 理由 |
|---|---|---|
| EdgeTAM エンコーダー（OpenVINO） | 55.5 → 32.3ms（−23ms） | 直前の画像の行列積の後のスピン待ちと、コアを取り合っていた |
| EdgeTAM デコード（OpenVINO、約 4 回） | 47.2 → 25.4ms（−22ms。1 回 約 12 → 6.4ms） | 同上。孤立実行では 1 回 5.3ms |
| 精緻化の NumPy / OpenCV の後処理 | 30.5 → 21.3ms（−9ms） | 同上（OpenCV・NumPy の演算もコア競合で遅くなる） |
| 粗い前景（KMeans・クラスタ代表・伝播） | 19.1 → 14.8ms（−4ms） | 行列積そのもの（1024×256 @ 256×1024）は 20 スレッドで 2.3ms、1 スレッドで 4.0ms と**少し遅くなる**が、競合が無くなって他の処理が速くなる |
| PE（OpenVINO） | 82.3 → 83.1ms（変化なし） | 影響を受けていない（理由は未確認。EdgeTAM エンコーダーの後に実行されるので、そのころには競合が終わっている可能性） |

**BLAS を使っている処理**（このリポジトリで行列積 `@` を呼ぶ箇所）:
- `core/common/mask_utils.py` の `knn_graph`: EdgeTAM 特徴の類似度 `features @ features.T`（1024×256 @ 256×1024）。**これが原因**。
- `core/common/coarse_segmentation.py` の `_classify_cluster`: `feature @ text_features.T`（1×512 @ 512×P）。小さく、単一スレッドで動くので、影響しない（直後のデコードは 7.9ms で、基準の 6.7ms とほぼ同じ）。

### 機構の確認（単体の実験）

EdgeTAM デコーダーを 20 回実行して中央値をとり、その前に BLAS の行列積（1024×256 @ 256×1024）を 1 回挟んだ。

| 行列積から次のデコードまで | BLAS 既定（20 スレッド） | BLAS 1 スレッド |
|---|---|---|
| （行列積なし。デコードのみ） | 7.4ms | 6.6ms |
| 行列積のすぐ後 | **29.4ms** | 7.4ms |
| 5ms 後 | **21.9ms** | 8.4ms |
| 50ms 後 | **25.5ms** | 13.0ms |
| 300ms 後 | 11.1ms | 14.5ms |

- 2.3ms の行列積の直後に、デコードが 7.4 → 29.4ms（約 4 倍）になり、50ms 後でも 25.5ms。1 スレッドでは 7.4ms のまま。
- 機構の推測: OpenBLAS のワーカースレッドが、呼び出し後もしばらくスピン待ち（既定のタイムアウトは約 100ms 程度の長さ）し、OpenVINO のピン止めされたスレッドとコアを取り合う。**これは測定から推測したもので、OpenBLAS の内部は確認していない**。
- 300ms 後・1 スレッドの値が増えるのは、sleep の間に CPU が省電力状態になる影響で、BLAS とは別（両方の設定で同様）。
- 実際の処理では、画像 N の伝播の行列積が、そのあとのデコード・NumPy 段（同じ画像）と、次の画像の EdgeTAM エンコーダー（先頭）を遅くする。
- `OPENBLAS_NUM_THREADS=1` / `OMP_NUM_THREADS=1` / `OPENBLAS_NUM_THREADS=2` は同じ効果（総時間 142.7 / 144.2 / 143.4ms、OV 6 スレッドで測定）。`OMP_WAIT_POLICY=PASSIVE`・`KMP_BLOCKTIME=0` は効かない（OpenMP ではない）。
- BLAS のスレッド数を変えても結果は同じ（17 枚の最終マップで画素差 0）。

### 実装

`core/openvino/runtime_utils.py`:
- `BLAS_NUM_THREADS = 1`、`limit_blas_threads()`: `OPENBLAS_NUM_THREADS` を `setdefault`（NumPy を import する前なら効く）し、`threadpoolctl.threadpool_limits(limits=1, user_api="blas")` を呼ぶ（import 済みの NumPy 向け。threadpoolctl は scikit-learn の依存で導入済み。無ければ環境変数だけ）。
- このモジュールの import 時と、`OVCLIPFeatureExtractor` / `OVEdgeTamRunner` の初期化時に呼ぶ（後から読み込まれたライブラリ向け）。
- PyTorch 版には入れない（合成 30 枚で 240ms（既定）と 251ms（BLAS 1）。差なし。PyTorch の推論は OpenVINO と違い、独自のスレッドプール）。

## 3. NumPy 段の外接矩形処理（結果は同じ）

`mask_utils.clean_mask` は、クラスごとのマスク（作業解像度 最大 1024×1024）に対して、連結成分・メディアンフィルタを全画素で実行していた。1 画像あたり約 4 回（クラス数 + 再推定）+ `remove_small_regions` で 3 回。

- 前景の**外接矩形（余白 1 画素）の中だけ**で処理するようにした（`bounding_slices`）。外は常に 0 なので、連結成分（8 近傍）もメディアンフィルタ（3×3、画像端は複製）も、全体で行うのと同じ結果になる。画像端に接する場合は余白をとらず、端の扱いも同じ。
- `remove_small_regions` のクラスごとの除去も、外接矩形の中だけで行う。背景の小さな穴を埋める処理（全画像の連結成分）は、外の背景との連結の扱いが変わるので、そのまま。
- 1024² で半径 150 の円: `clean_mask` 3.11ms → 1.15ms。精緻化の NumPy 段は、同一プロセスの交互測定で中央値 −4.9ms（総時間 −6.0ms）。物体が小さいほど効く。別プロセスの測定（上の表）では、後述の隙間埋め（約 1ms）を含めて 21.3 → 18.4ms。
- 検証: ランダムなマスク 300 ケース（`clean_mask` と `remove_small_regions`）で旧実装と一致、develop.py のサンプルなど 42 枚の最終マップが、変更前（HEAD）と画素差 0（隙間埋めを除く）。
- 前景内部の隙間埋め（`fill_narrow_gaps`、[semantic_refiner.md](semantic_refiner.md) §10.1）は、縮小したマスク（256×256）で閉処理するので、中央値 約 1ms、最大 約 9ms（全解像度の閉処理は約 11ms）。

## 4. 伝播（`knn_graph`）の高速化の限界

伝播は約 9ms（類似度の行列積 4.0ms + 上位 8 個の選択 `argpartition` 3.1ms + 疎行列の構築 0.6ms + 伝播 0.03ms）。**精度を変えずに縮まる余地はほぼ無い。**

- 疎行列を `indptr` から直接作る → −0.3ms。ただし疎行列の行内の添字の順が変わり、float32 の和の順序が変わって、1 枚で最終マップが 361 画素変わったので、**元に戻した**（−0.3ms のために結果を変えない）。
- 残りは計算量の下限に近い（1024×256×1024 の行列積は 1 スレッドで約 130 GFLOPS、上位選択は 1024 行 × 1024 要素）。
- 空間窓に限る（8×8 のブロックごとに、周囲 ±4 パッチの候補とだけ比べる）と −3ms（9.4 → 6.5ms）だが、**近傍が空間的に限られ、アルゴリズムが変わる**うえ、ブロック・余白の 2 定数が増える。精度を保てる保証がないので採らない。余白 8 以上では速くならない（9.5ms）。
- 対称行列の積（`ssyrk`）で半分にする案は、全行の上位選択に鏡映のコピー（4MB）が要り、差し引きがほぼ無い。

## 5. 試したが採らなかった案

| 案 | 結果 |
|---|---|
| OpenVINO のスレッド数を 6 / 8 に増やす | BLAS 1 のとき、合計 162.4（4）→ 142.7（6）→ 142.3（8）ms。**ユーザーの方針で増やさない**（4 のまま） |
| PE と EdgeTAM エンコーダーの並列実行（別スレッド、`ENABLE_CPU_PINNING: NO`） | 4 スレッドで逐次 110.6 → 並列 88.3ms（−22）。6 スレッドでは 83.7 → 81.2ms（−2.5）。ピン止めありでは 106.6 → 265.6ms（悪化）。実装が複雑なので見送り |
| デコードのバッチ化（デコーダーの入力は動的バッチ） | 3 クラス同時で 13.0ms、逐次 13.7ms（−5%）。クラスごとに点数が違うので、ラベル −1 でパディングしても、単独実行と結果が一致しない（logit の最大差 3.7）。見送り |
| INT8 | 既存の `_int8` モデルは重みの圧縮（`nncf.compress_weights`）のみで、CPU の速度向上は小さい見込み。活性化まで量子化する PTQ は、較正用の画像が要り、精度の確認も要る。未実施 |

## 6. 再現

```bash
# 段階別の時間（本体の config。結果は outputs/diagnosis/results_timing.json の "stages_now"）
python tools/experiments/diagnosis/exp_timing.py --task stages --key stages_now
# BLAS の既定に戻して測る（"stages_blas_default"。BLAS の制限だけを無効にした状態）: 環境変数と threadpoolctl を無効にする
OPENBLAS_NUM_THREADS=20 python -c "
import threadpoolctl; threadpoolctl.threadpool_limits = lambda *a, **k: None   # runtime_utils の制限を無効にする
import runpy, sys; sys.argv = ['exp_timing.py', '--task', 'stages', '--key', 'stages_blas_default']
runpy.run_path('tools/experiments/diagnosis/exp_timing.py', run_name='__main__')"
```

- 測定のばらつき: この PC は他のプロセス（WSL2、他のセッション）の負荷で、同じ設定でも PE が 77〜88ms で揺れる。変更の比較は、別プロセスで交互に 2 回以上測る。
- 実画像（17 枚）の処理時間は、合成より領域・デコードが多い（4〜9 回）。
